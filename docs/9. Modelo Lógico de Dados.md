# 9. Modelo Lógico de Dados

## 9.1 Objetivo

O modelo lógico de dados define as principais entidades do Sistema de Controle de Outorga Onerosa e seus relacionamentos.

Seu objetivo é representar o domínio do negócio de forma independente da tecnologia utilizada na implementação, servindo como referência para o desenvolvimento do banco de dados, APIs e regras de negócio.

As entidades descritas neste capítulo representam os objetos de negócio manipulados pelo sistema durante todo o ciclo de vida do processo administrativo.

---

# 9.2 Processo

O Processo é a entidade central do sistema.

Representa um processo administrativo de Outorga Onerosa e concentra todas as informações necessárias para seu acompanhamento.

Cada processo será identificado pelo número do Processo Administrativo (SEI) e possuirá informações provenientes dos sistemas corporativos integrados.

Um processo poderá possuir:

- um cálculo vigente;
- um parcelamento;
- uma ou mais parcelas;
- um ou mais SQLs;
- um histórico de movimentações.

---

# 9.3 Cálculo

Representa o cálculo oficial da Outorga Onerosa obtido por meio do Sistema de Cálculo.

O Sistema de Controle não realiza qualquer cálculo, sendo responsável apenas pelo armazenamento e gerenciamento das informações retornadas pela API.

Cada processo possuirá apenas um cálculo vigente.

O cálculo armazenará, entre outras informações:

- valor da Outorga;
- memória de cálculo;
- parâmetros utilizados;
- áreas consideradas;
- fatores aplicados;
- demais informações retornadas pela integração.

---

# 9.4 Parcelamento

Representa a forma de pagamento da Outorga Onerosa definida pela CAP.

Cada processo poderá possuir apenas um parcelamento ativo.

O parcelamento armazenará informações como:

- valor total;
- quantidade de parcelas;
- entrada;
- saldo devedor;
- situação do parcelamento.

---

# 9.5 Parcela

Representa cada obrigação financeira gerada pelo parcelamento.

Cada parcela possuirá seu próprio controle de situação.

Serão armazenadas informações como:

- número da parcela;
- valor;
- vencimento;
- situação;
- data do pagamento;
- observações administrativas.

Não será permitido o registro de pagamentos parciais para uma mesma parcela.

O sistema permitirá o registro de antecipação de parcelas, quando aplicável.

---

# 9.6 SQL

Representa os SQLs (Setor, Quadra e Lote) vinculados ao processo.

Um processo poderá possuir um ou mais SQLs.

Cada SQL poderá possuir um ou mais endereços associados.

As informações poderão ser obtidas automaticamente por meio das integrações com os sistemas corporativos.

---

# 9.7 Usuário

Representa os servidores responsáveis pela utilização do sistema.

Cada usuário estará vinculado a:

- perfil de acesso;
- coordenadoria;
- unidade administrativa;
- permissões do sistema.

Os perfis determinarão quais funcionalidades poderão ser executadas.

---

# 9.8 Coordenadoria

Representa a unidade administrativa responsável pela condução do processo.

Exemplos:

- RESID
- SERVIN
- COMIN
- CAEPP
- PARHIS
- CAP
- DEUSO

A coordenadoria será utilizada para controle de acesso, distribuição dos processos e geração de indicadores.

---

# 9.9 Histórico

Representa todas as movimentações realizadas durante o ciclo de vida do processo.

Cada movimentação registrará, no mínimo:

- usuário responsável;
- data e hora;
- ação executada;
- descrição da alteração.

Os registros do histórico serão imutáveis, garantindo rastreabilidade e auditoria.

---

# 9.11 Considerações

O modelo lógico apresentado neste documento representa o domínio funcional do Sistema de Controle de Outorga Onerosa.

A implementação física do banco de dados poderá conter entidades auxiliares, tabelas de apoio, estruturas de auditoria e otimizações necessárias ao desempenho da aplicação, desde que preservados os relacionamentos e regras de negócio definidos neste documento.

obs: Eu incluiria ainda uma entidade que não aparece para o usuário, mas que considero muito útil para a implementação:

Integração (ou ProcessoIntegracao)

Ela armazenaria cada consulta realizada aos sistemas externos (SEI, GeoSampa, Sistema de Cálculo), incluindo data/hora, sistema consultado, status da requisição, mensagem de erro (quando houver) e, opcionalmente, o payload de resposta. Isso facilita auditoria, reprocessamentos e diagnóstico de problemas sem misturar essas informações com a entidade Processo.
